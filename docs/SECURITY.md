# PerPay Security Specification

## Security Principles & Threat Mitigations

### 1. Non-Custodial Architecture
- Neither the frontend nor the backend ever stores, asks for, or logs customer private keys or seed phrases.
- All transaction signing occurs either client-side or via an isolated agent signer with strict allowance policies.

### 2. Private AI Generation Buffering
- AI completions generated by Groq are stored privately within Gateway storage until settlement is confirmed on Hedera.
- Response delivery is strictly prohibited prior to verified settlement confirmation.
- Direct streaming of completion deltas to an unpaid client is prevented.

### 3. Hedera Replay Protection & Uniqueness
- Every payment attempt tracks the unique Hedera transaction ID (`<payer>@<seconds>.<nanos>`).
- Database uniqueness constraints prevent any transaction ID from unlocking multiple invoices or generations.
- Transaction amounts, receiving account IDs (`0.0.YOUR_ACCOUNT_ID`), and network identifiers (`hedera:testnet`) are verified against the authoritative invoice record before response unlocking.

### 4. Account Spending Controls & Invoice Locks
- Each user account is restricted to **one outstanding unpaid invoice**.
- A user cannot initiate a new generation request while an earlier invoice remains unpaid.
- Platform-wide daily Groq spending budget and maximum token limits prevent runaway API expenses.

### 5. Internal Service Authentication
- All inter-service communications between `x402-service` and `gateway/` are authenticated using an internal pre-shared key passed in the `X-Internal-Secret` header.
- Requests failing authentication receive immediate HTTP 403 Forbidden responses.

### 6. Sanitized Logging & Environment Hygiene
- All sensitive fields (API keys, authorization headers, private keys, signed payloads) are filtered from application logs.
- Environment variable `.env` files and local databases (`*.db`) are ignored by Git (`.gitignore`).
